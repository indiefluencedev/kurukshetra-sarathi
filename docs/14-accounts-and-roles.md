# 14 · Accounts and roles

Better Auth, running in the Worker, storing users in the same D1 as everything
else. Chosen over a hosted identity service so the client owns this the way
they own the rest: the user table is a table in their own database, exportable
with the rest of it, with no per-user bill and nobody to ask for the data back.

---

## The shape of it

```
apps/api/src/auth.ts     config + the per-request factory
migrations/0003_auth.sql GENERATED by @better-auth/cli — never hand-edit
apps/web/src/features/account/
  auth.ts                the client: token, session, sign in/up/out
  Account.tsx            the screen
  Menu.tsx               the hamburger menu that reaches it
```

`makeAuth(env)` is a factory, not a module-level constant, because a D1 binding
only exists inside a request. There is nothing to construct at import time.

---

## Bearer tokens, not cookies

Not a preference. The app is served from `kuk-saarthi.pages.dev` and the Worker
answers on `kuk-saarthi-api.….workers.dev`. Those are different **sites**, so a
session cookie set by the Worker is a third-party cookie. Safari blocks those
outright and Chrome is removing them — login would silently fail on exactly the
iPhones this app is used on.

So the session travels as an `Authorization: Bearer …` header the app keeps in
`localStorage`. Two consequences worth being honest about:

- `localStorage` is readable by any script on the origin. Acceptable **only**
  while the app ships no third-party scripts and the token unlocks nothing but
  saved itineraries. Both are true today. If either stops being true, this
  needs revisiting.
- `set-auth-token` must be in `access-control-expose-headers` or the app cannot
  read the token it was just issued. A cross-origin response hides every header
  not on that list, and the failure looks like a successful sign-in that leaves
  you logged out.

**The real fix is one origin.** Put the Worker on a route of the same custom
domain as the app (`kurukshetra.example.org/api/*`) and cookies become
first-party. That needs a domain we do not have yet; the bearer plugin keeps
working either way, so it does not block.

## Roles

One extra field on the user, `role`, either `visitor` (the default) or `admin`.

```ts
role: { type: "string", required: false, defaultValue: "visitor", input: false }
```

`input: false` is the whole security of it. Without it, `role` is an ordinary
profile field and anyone could sign up posting `{"role":"admin"}`. Verified
against the live Worker: that request returns a user with role `visitor`, and
its token gets 403 from `/admin/events`.

Promotion is therefore a deliberate act against the database:

```bash
npx wrangler d1 execute discover_kurukshetra --remote \
  --command "update user set role='admin' where email='someone@example.org'"
```

Crude, and correct for a handful of Board members. It becomes a process when
there are enough people that this is annoying — see TASKS.md.

### What the guard does

`admin(req, env)` in `index.ts` returns the email **only** for a signed-in user
whose role is `admin`, and an empty string for everything else — anonymous,
signed-in visitor, expired token, or an error reading the session. Every caller
treats empty as refuse, so a visitor poking at `/admin` is indistinguishable
from a stranger.

The dashboard **page** is served unauthenticated on purpose. It is a sign-in
form and an empty shell, and every route it calls is guarded. A 403 there would
leave the Board with a login screen they must already be logged in to reach.

## `nodejs_compat` is required

Better Auth reaches for `node:crypto` and `node:async_hooks`. Without the flag
the Worker does not fail at deploy — it fails to **start**, with
`No such module "node:crypto"`. It is set in `wrangler.toml`.

## The schema is generated

```bash
npx @better-auth/cli generate --config src/auth.ts --output migrations/000N_auth.sql
```

Do not hand-edit `0003_auth.sql` to add a column. The library and the table
shape have to agree exactly, and hand-editing is how they stop agreeing. Change
`auth.ts` and regenerate into a **new** migration.

Generation needs a database to introspect — the CLI checks what already exists
so it can emit only what is missing. `auth.ts` exports a stub that answers
introspection with "no tables" for exactly this. Pointing the CLI at a live D1
instead would make the generated schema depend on which database happened to be
connected.

## Client behaviour, and why

Three decisions in `features/account/auth.ts` are about failure, not features:

- **`loadSession()` is never awaited before first paint.** Every screen works
  signed out. An auth round trip must not be the thing the app waits on.
- **A network failure resolves to signed OUT.** Showing someone their name and
  an empty saved list because the server was unreachable is worse than showing
  a sign-in button.
- **`signOut()` clears locally first and tells the server after.** On a
  borrowed phone, tapping sign out has to sign you out even with no signal.

The client is hand-written against the HTTP endpoints rather than using Better
Auth's React client. The library brings its own store and hooks; this app has
one state model (`S` + `bump()`) that every feature uses, and adding a second
one to save forty lines would leave two ideas of "current state" in an app that
deliberately has one.

## Google sign-in

Coded and dormant. The provider is registered **only** when both credentials
are present — passing an empty id does not disable a provider, it produces a
button that fails at Google with an unhelpful error, so the app hides the
button entirely instead.

To turn it on:

1. Google Cloud Console → Credentials → OAuth client ID → Web application.
2. Authorised redirect URI:
   `https://kuk-saarthi-api.indiefluence-in-media.workers.dev/api/auth/callback/google`
   — it must match `API_URL` in `wrangler.toml` exactly.
3. `npx wrangler secret put GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`
4. `npm run deploy`

## What is NOT built

Named here because each is a real gap, not a nicety:

- **No password reset.** Someone who forgets is locked out with no route back.
- **No email verification.** Anyone can sign up as anyone's address.
- **No rate limiting.** Sign-in is unthrottled, so guessing is free.
- **Saved plans do not sync.** The account currently buys the user nothing.

The first two both need an email sender. Cloudflare Email Sending is free and
in the same account. `requireEmailVerification` should be turned on *together*
with the sender — turning it on first locks out every new sign-up.

## Rate limiting

Counters live in D1 (`rateLimit` table, migration 0004), not in memory.

In-memory limiting is the library default and is **worthless on Workers**: a
request lands on whichever isolate is free, possibly in another city, so an
attacker gets a clean allowance every time and the limit never bites. Putting
the counters in the database is what makes the number mean anything.

| route | window | max |
|---|---|---|
| `/sign-in/email` | 5 min | 8 |
| `/sign-up/email` | 1 hour | 5 |
| `/change-password` | 5 min | 5 |
| everything else | 1 min | 30 |

### The bucket key, which is the part that matters

```ts
advanced: { ipAddress: { ipAddressHeaders: ["cf-connecting-ip"] } }
```

Without this Better Auth finds no trusted IP header and files every request
under a single key — `no-trusted-ip|/sign-in/email`. The limit then applies to
**everyone at once**, so one person guessing passwords locks the entire
district out of signing in. That is a denial of service handed to any
attacker, delivered by the security feature.

Verified before and after: one shared bucket at first, two separate per-IP
buckets afterwards, and the production table keyed by the real client address.

`cf-connecting-ip` specifically, because Cloudflare sets it on every request
and overwrites any inbound copy. Trusting `x-forwarded-for` instead would let
an attacker vary one header per request and never be limited at all.

> **Testing note.** You cannot verify this from outside by sending your own
> `CF-Connecting-IP` — Cloudflare rejects such a request with `error code:
> 1000` before it reaches the Worker. That refusal is the protection working.
> Check the `rateLimit` table's keys instead.

## Push notifications

Not authentication, but it shares `/config` and the same "ask once, carefully"
problem.

`Notification.requestPermission()` may be answered **once**. "Block" is
permanent from the page's side — there is no second prompt, only a browser
settings screen most people will never find. So the app shows a card first
(`features/notify/NotifyCard.tsx`) explaining what the notifications are, and
only a tap on "Yes" reaches the browser. "Not now" can be revisited from
Settings; "Block" cannot be revisited at all.

The service worker is generated by Workbox, so there is no source file of ours
to add listeners to. `public/push-sw.js` is pulled in with
`workbox.importScripts` — the precache logic stays generated and untouched,
and push is twenty readable lines. That file never passes through the bundler,
so it must stay plain JS.

Settings reports whether the device is **subscribed**, not whether permission
was granted. Those come apart: a browser can hold "granted" while the
subscription was never registered or has been expired by the push service, and
showing "on" then would be the app lying about something the visitor cannot
check.

`enablePush()` returns true only once the Worker has accepted the endpoint.
Permission without registration means silence, and a promise of notifications
that never arrive is worse than never having asked.
