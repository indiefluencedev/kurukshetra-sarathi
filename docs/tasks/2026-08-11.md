## Task 1 — Move off D1 onto Neon Postgres, then shut D1 down

**Status:** migrated and verified **locally**. Production is still the old
Worker on D1 — nothing has been deployed and nothing has been deleted. The two
remaining steps are `npm run deploy` (with `NEON_DB_URL` set as a secret) and
then disabling D1.

### Done

- **Schema.** `apps/api/db/migrations/`, four files, applied by
  `apps/api/db/migrate.mjs` — a 60-line runner that replaces
  `wrangler d1 migrations apply`, tracks what has run in `_migrations`, and
  wraps each file in a transaction (which D1 could not do).
- **Better Auth's tables were regenerated, not translated.** `emailVerified`
  is a real boolean now instead of an integer, and every date is `timestamptz`
  instead of SQLite's string-in-a-`date`-column. The rate-limit table the D1
  schema needed as its own migration comes out of the CLI with the rest.
- **`store.neon.ts`** replaces `store.d1.ts`. The `Store` interface in
  `store.ts` promised this would be one file, and it was: `?` → `$1`,
  `INSERT OR IGNORE` → `ON CONFLICT DO NOTHING`, `SET n = n + 1` →
  `SET n = rev.n + 1` (Postgres will not resolve the bare column). Everything
  else is the same queries.
- **Two drivers, one dependency.** The store uses `neon()` — HTTP, one round
  trip, no socket to leak when a Worker isolate is discarded. Better Auth uses
  `Pool` over a WebSocket, because sign-up and sign-in run in *interactive*
  transactions and the HTTP endpoint only accepts a transaction whose
  statements are all known up front. That distinction is the one non-obvious
  thing in the whole migration.
- **103 rows copied** by `db/copy-from-d1.mjs`, in one transaction, from the
  snapshot rather than from live D1. Sessions were deliberately not copied.
- **Dead code removed:** `store.d1.ts`, `migrations/`, `inspect-db.mjs`,
  `find-local-db.mjs`, `seed.sql`, and the `kysely-d1` dependency.
  `import-content.mjs` now writes to Postgres with parameters instead of
  emitting hand-escaped SQL for wrangler to run — one apostrophe in a blurb
  used to be a syntax error in the middle of a bulk import.

**Why:** the store moves to Neon (Postgres 18.4,
`ep-green-hill-az88sbta-pooler.c-3.ap-southeast-1.aws.neon.tech`, Singapore —

**Ordering is not negotiable.** D1 holds the only copy of the two admin
accounts and every place the Board has edited. Nothing is deleted until Neon
is serving and verified. The order is: build Neon → copy → verify → cut over →
*then* disable D1.

### What the migration actually touches

exactly one file". That holds, with two exceptions found today:

### Questions that came up, and how they were answered

- **Sessions — copy or drop?** Dropped. Two browsers sign in once more; the
  alternative was porting Better Auth's session rows by hand for a table whose
  contents expire anyway.
- **`audit.id`** was `INTEGER PRIMARY KEY AUTOINCREMENT`. It is now
  `GENERATED BY DEFAULT AS IDENTITY` — *by default*, not *always*, so the copy
  could keep the ids the rows already had. A sequence does not notice ids
  inserted past it, so the copy script resets it at the end. Without that the
  next audit write collides with a copied row and the whole edit fails on the
  *audit* insert, after the edit itself has landed. Confirmed working: copied
  ids 1–2, next writes 3–4.
- **`emailVerified`** was an integer under SQLite. Regenerating Better Auth's
  schema rather than translating it by hand made it a boolean, which is what
  the library expected all along.

## Task 3 — One command to run the whole thing

**Done.** `npm run dev` from the repo root starts the Worker and the app
together. Three terminals became one.

It is `dev.mjs`, a script, and not `"dev": "a & b"` in package.json — for three
reasons that all came up while testing it:

- Two servers on one terminal need labels, or you cannot tell which one printed
  the error. Output is tagged `api │` and `web │`.
- Ctrl-C on a shell `&` leaves orphans holding 8787 and 5173, and the next run
  fails in a way that looks like a code problem. Either half exiting now takes
  the other down, with SIGKILL after two seconds for wrangler, which can sit on
  its port mid-build.
- **The two halves have to agree on one hostname**, and that is a lookup rather
  than a constant.

### The hostname, which is the actual content of this change

A phone cannot resolve `localhost` to this laptop. So both servers bind to
every interface (`vite --host`, `wrangler dev --ip 0.0.0.0`) and the app is
told to call the API at this machine's LAN address, which the laptop can reach
too — one value, not a desktop case and a phone case.

Two things had to move for that to work end to end:

- **`VITE_CONTENT_URL` is now set in development**, to the local Worker. It was
  deliberately unset, so `npm run dev` read the bundled catalogue and never
  called the API at all. That was right when the database was a copy on this
  laptop; it is wrong now, because the thing being worked on is whether an
  admin edit reaches the app — which cannot be seen if the app never asks. The
  cost is real and worth naming: since Neon there is one database, so those are
  live rows. `npm run web:dev` + `npm run api:dev` gets the old behaviour back.
- **`trustedOrigins` takes a comma-separated list.** Better Auth refuses an
  Origin it was not told about, and dev serves the app from two legitimate
  addresses — `localhost:5173` and `192.168.x.x:5173`. Listing one means
  sign-in works on the desktop and fails on the phone with a CORS error that
  says nothing about origins. Production passes a single value and splits to a
  list of one.

Verified: both addresses return 200 on `/content/places.json` and
`/api/auth/get-session`, and the transformed module served by Vite carries the
LAN API URL.

## Task 4 — Drizzle removed

**Done.** `drizzle-kit`, `drizzle-orm`, `@libsql/client`, `drizzle.config.ts`,
`apps/api/drizzle/` and the `db` / `db:remote` / `db:prod` / `db:pull` scripts
are gone.

It was only ever a viewer, and it existed because looking at D1 was awkward —
the Cloudflare console could not really show you rows, so a local Studio
pointed at a SQLite file was the least bad option. Neon has a console with
tables, a SQL editor and query history, already authenticated. The reason is
gone, so the tool goes with it.

`npm run inspect` went too. It refused a migration when the database held
unexpected tables, which mattered because `discover_kurukshetra` was a
pre-existing database and because a failed D1 migration could not roll back.
`db/migrate.mjs` records what it has applied and wraps each file in a
transaction — the same guarantee, obtained honestly rather than by looking
first.

## Task 5 — Email verification and password reset

**Built and verified locally. One manual step outstanding.**

Two of the oldest items on the blocking list, and they were always one item:
both need a sender. Cloudflare Email Sending, from `noreply@brainybeans.space`
— chosen because it is an active zone in the same account, with the caveat that
the domain has nothing to do with Kurukshetra and recipients will notice.

- `src/email.ts` — the sender and both templates. English and Hindi in every
  email, because Better Auth hands us a user row and there is no language on
  it; the alternatives were a column, a guess, or defaulting everyone to
  English.
- **A failed send never fails the operation behind it.** An account is worth
  more than its welcome email. The error is logged with its code, because the
  failure that matters — the domain not being onboarded — is every send rather
  than one.
- **Verification is required.** Sign-up returns `token: null`; signing in
  before confirming is `403 EMAIL_NOT_VERIFIED`. The app says to go and read
  the email instead of sending someone to the home screen signed out.
- Migration `0005` marks the two pre-existing accounts verified, scoped by
  `createdAt` so it cannot catch a future sign-up. Without it, deploying the
  flag locks the Board out of its own dashboard.
- **Neither form reveals whether an address is registered.** Reset requests
  answer 200 either way.
- `Account.tsx` gained two states — ask for a link, choose a new password — and
  strips `?reset=` / `?verified=` from the URL as soon as it reads them. A live
  reset token in the address bar survives screenshots and restored tabs.

### A bug this found, worth recording

The first verification email built its link to **production** —
`kuk-saarthi-api…workers.dev` — from a laptop. `dev.mjs` was passing `APP_URL`
as an environment variable, and **wrangler does not read Worker vars off the
shell**; they come from `wrangler.toml` and `.dev.vars`. The override looked
like it worked and did nothing. It is `--var` now.

It was only visible because `wrangler dev` writes the email to
`.wrangler/tmp/email/` instead of sending it, and reading that file was the
last check rather than the first. An earlier "both origins return 200" test had
already given a false pass on the same variable.

## Task 6 — Mail is configuration, and a code you can read from the database

**Done.**

- **`EMAIL_PROVIDER` / `EMAIL_FROM` / `EMAIL_NAME` / `RESEND_API_KEY`.** Nothing
  about a sender is compiled in any more. `cloudflare` uses the binding,
  `resend` is one `fetch`, `log` prints the message and sends nothing.
  `deliver()` is the only function that has heard of a provider; the templates
  have not. Moving to Resend is two variables and a secret.
  Verified by running a second Worker with `--var EMAIL_PROVIDER:log` and
  watching it log rather than touch the binding.
- **Verification is a six-digit code now**, via Better Auth's emailOTP plugin.
  `npm run otp [email]` reads it out of `verification` and prints it with the
  time left — which is the whole point today, since no mail is being delivered.
  `storeOTP: "plain"` is what makes that readable, and is **a live credential

- The app gained the code screen: numeric input with `one-time-code` autofill,
  a resend button, and sign-in with an unconfirmed address now routes to that
  screen with a fresh code instead of showing "email not verified".

## Task 6b — Resend, and the sending domain

**Switched. Waiting on DNS.**

The provider swap was the thing Task 6 was built for, and it cost exactly what
it was supposed to: `EMAIL_PROVIDER`, `EMAIL_FROM`, `RESEND_API_KEY`. **No code
was touched.**

Cloudflare Email Sending is abandoned rather than finished — every attempt at
`wrangler email sending enable` answered `2036 Unauthorized`, on both the OAuth
login and the API token, and the API is in beta. The binding stays in
`wrangler.toml`, unused, as the fallback.

`kkr.indietribe.space` is registered with Resend (`ap-northeast-1`) and
**pending**. `indietribe.space` is **not on Cloudflare** — `dig NS` says
`ns1/ns2.dns-parking.com`, which is Hostinger — so the Cloudflare token here
cannot write the records and they have to be added by hand there. Names are
relative to the `indietribe.space` zone:

| Type | Name | Value |
|---|---|---|
| TXT | `resend._domainkey.kkr` | the DKIM `p=…` key |
| MX | `send.kkr` | `feedback-smtp.ap-northeast-1.amazonses.com`, priority 10 |
| TXT | `send.kkr` | `v=spf1 include:amazonses.com ~all` |

The existing `v=spf1 include:_spf.mail.hostinger.com ~all` at `kkr` does not
conflict: that is the domain's own mail, these are on `send.kkr`.

`npm run email:status` prints the records and what is still pending, `--verify`
asks Resend to re-check, and passing an address sends a real test once it
verifies. It exists because "the email did not arrive" has four causes — wrong
key, unverified domain, unpropagated record, suppressed recipient — and one
command answering all four beats another browser tab.

Confirmed live: sign-up returns **200**, the Resend path reports
`resend 403: The kkr.indietribe.space domain is not verified`, and the account
is still created with a readable code. That is the graceful-degradation
behaviour working as designed — and also exactly why the failure is easy to
miss.

## Task 6c — One env file, and what production is actually missing

**Done.**

`.dev.vars` is gone. There is one `apps/api/.env`, gitignored and commented
line by line, read by both halves:

```
the Worker    wrangler dev --env-file=.env
the scripts   node --env-file=.env …
```

Two files existed because wrangler historically could not read a plain `.env`.
It can since 4.x, and the second file was costing what duplicated config always
costs — the same secret typed twice, drifting. `.env.example` replaces
`.dev.vars.example`.

`--env-file` is on `dev` only and deliberately **not** on `deploy`: a deploy
that swept this file up would push local values into production, which is the
one direction these must never travel.

Verified: the Worker loads all thirteen variables from it, and the scripts read
the same file — sign-up 200, `npm run otp` returns a code.

### Production, checked against the live Worker

The screenshot was right — the deployment is behind the code. Nothing is
broken; it is undeployed.

| | live | needed |
|---|---|---|
| `NEON_DB_URL` | **absent** | the database |
| `RESEND_API_KEY` | absent | provider is `resend` |
| `EMAIL_PROVIDER` / `_FROM` / `_NAME` | absent | ride along with `wrangler.toml` |
| `AUTH_SECRET`, `VAPID_PUBLIC`, `VAPID_PRIVATE` | ✅ | — |

## Task 6d — One copy of the secrets, and the one that cannot be copied

**Partly done, and the limit is not ours.**

The ask was to fill `.env` with the values already in Cloudflare. **Two of the
three cannot be.** A Worker secret is write-only — no API, no CLI flag, no
dashboard button returns the plaintext. That is the point of a secret store,
not a permission we are missing, and no amount of token-widening changes it.

| | |
|---|---|
| `VAPID_PUBLIC` | **recovered** — not from the secret store but from the deployed Worker's own `GET /vapid`. It is a public key; being published is its job. The value in `.env` is genuinely production's. |
| `AUTH_SECRET` | unrecoverable. `.env` holds a local-only value, labelled as such. |
| `VAPID_PRIVATE` | unrecoverable. Left empty, which is a clean way to develop — `/config` reports no key and the app never offers notifications. |

For the two unrecoverable ones the only route to one copy is **replacing both
sides at once**. Today that costs 2 signed-out sessions and 2 stranded push
subscriptions, against **0 notifications ever sent**. It will not stay that
cheap; the commands are in `.env` beside each value.

### Also fixed on the way through

`EMAIL_FROM` had a **leading space** — `EMAIL_FROM= noreply@…`. `node
--env-file` keeps it, so the address would have been `" noreply@…"` and Resend
would have rejected every send with a message about the address rather than the
space. Caught while rebuilding the file, not by anything that would have warned.

The file was rebuilt around the five values already in it, with the missing
eight restored and every one carrying a comment saying what it does, what
breaks without it, and where its production counterpart lives. 15 variables
load; `/config`, `/img/` and the app all still answer 200.

## Task 7 — R2 and the database in the same place

**Done, and it was not what it looked like.**

The report was that images and R2 were not linked to Neon. In production they
are, and always were: the bucket holds **99 objects**, the content rows in Neon
reference **99 distinct images**, and the deployed Worker serves them 200.
Nothing was broken there.

What was broken was **local development**, and it was collateral from the Neon
move. `wrangler dev` binds R2 to an empty local emulation by default. That was
right when the database was local too — both halves were copies. Once the
database became the real Neon one, the halves disagreed: the dashboard showed
real content listing 99 photographs against a bucket holding none, so every
`/img/` 404'd and the media library was empty.

The fix is `remote = true` on the binding — one line, and now `npm run dev`
serves the real photographs:

```
200  11430b  /img/brahma-sarovar     (404 before)
200  20996b  /img/jyotisar
200  14708b  /img/anubhav-kendra
200   9412b  /img/brahma-sarovar-2
```

The cost is the one the database already carries and it is worth saying out
loud: **an upload or a delete from a laptop is now an upload or a delete in
production.**
